## **交流记录详情**

### **1\. 技术选型与项目骨架**

**涉及人员**：全员

**涉及事项**：

- 确定项目名称为"BBS论坛系统"，面向校内用户，涵盖帖子交流、板块浏览、需求悬赏、积分互动和后台管理。
- 后端框架选定 Spring Boot 2.7.18，ORM 框架选定 MyBatis-Plus 3.5.7（支持分页、逻辑删除、乐观锁）。
- 前端选定 Thymeleaf 模板引擎 + Bootstrap 5.3。
- 富文本编辑器选定 wangEditor（轻量、API 简单、适合课程项目），帖子内容以 HTML 格式存储，后续需做 XSS 安全过滤。
- 数据库选定 MySQL 8.0，缓存选定 Redis 6.x（用于 JWT 黑名单和热点数据缓存）。
- 项目分包结构确定：controller、service、service.impl、mapper、entity、dto、vo、common、config、interceptor、annotation、aspect。
- 系统用户分两类：普通用户（注册、登录、浏览、发帖、回复、需求悬赏、积分查询）和管理员（额外可管理用户、板块、帖子、查看操作日志）。
- **划分五个核心模块：**
    - **系统基础架构**（王陈鸿）：统一响应、统一异常处理、JWT 认证、拦截器、Redis 缓存。
    - **用户管理**（刘源浩）：注册、登录、个人资料、积分查询与流水。
    - **论坛帖子**（乐振涛）：帖子 CRUD、回复树、HTML 过滤、浏览量。
    - **论坛管理**（刘劲翀）：板块管理、帖子管理（置顶/加精/删除）、用户状态管理、操作日志。
    - **需求悬赏**（黄康毅）：需求发布、回复、采纳、关闭、积分冻结与转移。
- 确认模块间依赖：基础架构为所有模块提供认证和公共能力；帖子模块依赖用户模块获取作者信息；管理模块依赖帖子模块和用户模块；需求悬赏模块依赖用户模块的积分服务。

**项目前端**采用 Thymeleaf 模板引擎 + Bootstrap 5.3**，后端模块负责人对应编写前端页面**。

- **王陈鸿**（系统基础架构）：公共页面框架，比如统一布局模板（header/footer/sidebar）、错误页面、登录注册页面的基础结构。
- **刘源浩**（用户管理）：注册页、登录页、个人中心页、积分流水页。
- **乐振涛**（论坛帖子）：首页帖子列表、板块帖子列表、帖子详情页（含回复展示）、发帖/编辑帖子页。富文本编辑器 wangEditor 的集成。
- **刘劲翀**（论坛管理）：后台管理页面，包括板块管理、帖子管理（置顶/加精/删除的操作界面）、用户管理、操作日志查看。
- **黄康毅**（需求悬赏）：需求悬赏列表页、需求详情页、发布需求页、采纳/关闭需求的操作界面。

**决策结果**：五模块分工明确，各成员独立开发各自模块包括对应前端页面。

页面模板统一放在 resources/templates 下，按模块分子目录（user/、post/、demand/、board/、admin/、common/）。公共样式放在 static/css/bbs.css，公共 JS 放 static/js/common.js。

wangEditor + Service 层 XSS 过滤 + 分层内嵌模块结构。

### **2\. 数据库设计**

**涉及人员**：全员

**涉及事项**：

- 确定八张核心表：user、board、post、reply、demand、demand_reply、score_record、admin_log。
- **用户表**（刘源浩主导）：role（0普通/1管理）、status（0待审核/1正常/2禁用）、score、frozen_score、version（乐观锁）、login_count、last_login_time。username 设唯一索引。
- **板块表**（刘劲翀主导）：name、description、sort_order、post_count、status。
- **帖子表**（乐振涛主导）：board_id、user_id、title、content（longtext，存 HTML）、view_count、reply_count、is_top（0普通/1板块置顶/2全局置顶）、is_essence、status、last_reply_time。建立复合索引 (status, is_top, create_time)。
- **回复表**（乐振涛主导）：post_id、user_id、parent_id（自关联，NULL 为一级回复）、floor（楼层号）、content。业务层限制嵌套深度 ≤ 3 层。
- **需求悬赏表**（黄康毅主导）：user_id、score、status（0进行中/1已解决/2已关闭）、resolver_id、adopt_reply_id。需求回复表 demand_reply 为平铺结构，不支持楼中楼。
- **积分记录表**（刘源浩主导）：type（1获得/2支出/3冻结/4解冻）、amount、balance、source_type、source_id。
- **管理员日志表**（刘劲翀主导）：admin_id、action、target_type、target_id、ip。
- 外键策略：帖子删除 → 级联删除回复；用户删除 → 级联删除其帖子/回复/需求/积分记录；需求中的 resolver_id 和 adopt_reply_id 设为 SET NULL。
- 所有表含 deleted、create_time、update_time 通用字段。

**决策结果**：王陈鸿编写 init.sql 并插入初始数据（管理员 admin、测试用户 testuser、四个默认板块）。

### **3\. JWT拦截器方案**

**涉及人员**：王陈鸿、刘源浩、乐振涛

**讨论焦点**：GET请求如何处理

**事项**：

- **GET 请求问题**：帖子列表、详情页需同时支持登录和未登录用户。王陈鸿初版对 GET 全部放行不校验 Token。乐振涛指出这导致登录用户在 GET 请求中拿不到身份信息，前端无法判断是否显示编辑按钮。讨论后改为"可选认证"：GET 静默解析 Token，成功则注入用户信息到 request，失败不拦截。王陈鸿在拦截器中新增 tryInjectUserAttributes() 方法。
- **Token 黑名单**：退出登录后 Token 应失效。缩短有效期方案简单但有安全窗口期；Redis 黑名单更精确但多一步查询。退出为低频操作，确定用 Redis 黑名单，key 为 blacklist:token，过期时间与 Token 剩余有效期一致。
- **用户信息传递**：ThreadLocal vs request.setAttribute。ThreadLocal 有内存泄漏风险且不适合 Web 请求生命周期，选 request.setAttribute。

**决策**：GET 可选认证、Redis 黑名单、request 传递用户信息。

### **4\. 跨模块接口对接**

**涉及人员**：刘源浩、乐振涛、黄康毅

**讨论焦点**：VO字段不一致、用户信息获取方式

**事项**：

- **命名冲突**：帖子列表页作者名不显示。排查发现刘源浩 UserVO 返回 userName（首字母大写），乐振涛 PostVO 解析 username（全小写），JSON 绑定失败。双方此前未约定命名规范。统一为全小写驼峰：username、realName、avatar。
- **用户信息获取方式**：帖子列表需展示作者名和头像。乐振涛用 MyBatis JOIN 直接查，刘源浩认为绕过用户模块封装，后续用户表变动时帖子 SQL 也要改。乐振涛回应逐条调接口会有 N+1 查询问题。折中：列表/详情用 JOIN（性能优先），单点查询如查看他人主页调接口（解耦优先）。
- **积分流水接口**：黄康毅需要查询用户积分判断是否足够冻结，需刘源浩提供接口。确定参数为 userId + type（可选）+ page。

**决策**：统一全小写驼峰、分场景定用户信息获取方案、积分流水接口参数确认。

### **5\. 帖子模块联调**

**涉及人员**：乐振涛、王陈鸿

**讨论焦点**：XSS过滤返工、权限方案升级

**事项**：

- **XSS 过滤踩坑**：初版用 Jsoup.clean(html, Whitelist.basic())，把加粗、换行、图片等合法格式也洗掉了。原因：Whitelist.basic() 只保基础文本标签。乐振涛重写 cleanHtml()：手动解析 DOM，仅移除 &lt;script&gt;、&lt;iframe&gt;、&lt;object&gt; 等危险标签和 on\* 事件属性，保留安全标签。王陈鸿 review 后补充 javascript: 伪协议过滤。
- **回复树性能**：初版递归查询，30 条回复产生 31 次 SQL。乐振涛改为一次性查出全部回复，Java 内存中用 LinkedHashMap 按 parentId 分组构建树。王陈鸿建议补 parent_id 索引降低单次查询耗时。
- **权限硬编码升级**：原方案每处判断 post.userId == currentUserId，王陈鸿指出管理员也应能删帖且逻辑不宜散落各处。统一用 @RequireOwner 注解 + AOP，乐振涛改为使用注解。

**决策**：白名单+移除危险标签方案、一次性查询+内存组树、权限统一用注解。

### **6\. 管理员切面设计**

**涉及人员**：刘劲翀、王陈鸿

**讨论焦点**：注解粒度、日志字段

**事项**：

- **注解是否拆分**：查看类和操作类接口是否需要两个注解（@RequireAdminRead / @RequireAdminWrite）。讨论认为当前管理员角色单一，拆分增加复杂度，统一用 @RequireRole。
- **操作类型推断**：切面根据方法名推断操作（含 "Top" 则为"帖子置顶"），刘劲翀提出是否改用注解属性显式声明。王陈鸿认为当前命名规范足够，额外属性增加维护负担。暂用方法名推断。
- **oldValue 字段**：是否需要记录操作前旧值（如置顶前 is_top=0）。刘劲翀认为审计需要。部分操作如删除需额外查询一次，性能影响可接受，保留。

**决策**：统一 @RequireRole、方法名推断操作类型、保留 oldValue。

### **7\. 积分与事务方案**

**涉及人员**：黄康毅、刘源浩

**讨论焦点**：并发锁选型、操作顺序

**事项**：

- **乐观锁 vs 分布式锁**：用户同时发布多个需求可能积分超扣。黄康毅倾向 Redis 分布式锁，刘源浩倾向乐观锁——积分扣减就是数据库 UPDATE，version 字段天然适配。折中：默认乐观锁，压测冲突率超 10% 再加分布式锁。
- **事务传播**：DemandService.publish() 调 ScoreService.freeze()，事务能否跨 Service？刘源浩确认 @Transactional 默认 REQUIRED，外层事务自动传播到内层，一次提交或回滚。
- **操作顺序**：采纳时先改需求状态再转账，还是反过来？黄康毅指出先改状态再转账，转账失败时状态未回滚。确定先转账再改状态——转账失败直接停止，配合 @Transactional 保证一致性。

**决策**：乐观锁为主、事务传播确认、先积分后状态。

### **8\. 公共规范统一**

**涉及人员**：全员

**讨论焦点**：参数格式不一致

**事项**：

- **XSS 方法公共化**：乐振涛的 cleanHtml() 从 PostServiceImpl 抽到 common.HtmlUtil，黄康毅的需求回复直接调用。
- **分页参数**：用户模块用 pageNum/pageSize，帖子模块用 current/size，前端需适配两套。统一为 current/size。
- **日期格式**：前后端出现 2024-03-15T10:30:00 和 2024-03-15 10:30:00 混用。在 application.yml 统一配置 Jackson 格式为 yyyy-MM-dd HH:mm:ss。
- **异常消息**：各模块有的返回"操作失败"，有的返回详细原因。统一要求 BusinessException 必须携带用户可理解的明确提示。

**决策**：四条规范全部统一，写入项目文档。

### **9\. 云部署与故障**

**涉及人员**：全员

**讨论焦点**：部署方式、线上故障排查

**事项**：

- **Docker vs Jar**：Docker 可复用但对全员学习成本高，选择 Jar + 宝塔面板。
- **RDS vs 自建 MySQL**：RDS 稳定免运维但费用高，课程项目数据量小、周期短，选自建 MySQL 宝塔一键安装，定期手动备份。
- **线上故障排查**：
    - 首次访问 502：安全组未开 8080 端口，阿里云默认只开 22/80/443，添加规则后解决。
    - 数据库连接超时：原用 RDS 时白名单未加服务器 IP，后改自建 MySQL 无需白名单。
    - Jar 启动即退出：lsof -i:8080 发现端口被旧进程占用，kill 后正常。

**决策**：Jar + 宝塔 + 自建 MySQL。三类故障排查过程全员备忘。
